# The harness hook — Stage C wiring, and the adapters that speak it

`loxodonta hook` turns a `PostToolUse` payload (JSON on stdin) into one chained entry. Claude Code was the first harness to send one and is the reference throughout this page; Codex CLI sends the same shape natively, and the OpenAI Agents SDK adapter produces it from tracing spans — see [Other harnesses](#other-harnesses) below (ADR-0020). This is the completeness mechanism promised in SPEC §8 and ADR-0002: the harness fires the hook after every **completed** tool call, so the log call sits outside the writer's volition — the agent cannot skip its own receipt, and a session becomes a verifiable flight recording with no cooperation from the agent at all. (A failed or denied call fires no hook — the harness's rule, not ours — and the supervisor's witness counts by exactly the same rule, so nothing is owed for it. The same edge holds for what the harness does on the session's behalf outside any tool call: a worktree it merges or prunes when a session leaves it, a context compaction, its own git plumbing. No tool event exists for those, so no hook fires and no receipt is owed; the commits such a merge carries were each made by a tool call and have their receipts, and git's reflog records the moment the branch pointer moved. Coverage is completed tool calls, and it says so.)

## Wiring

In the project's `.claude/settings.json` (or your user settings):

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "python3 /absolute/path/to/loxodonta.py hook"
          }
        ]
      }
    ]
  }
}
```

- With no `--log-dir`, the adapter reads the `CLAUDE_PROJECT_DIR` environment variable the harness sets for hooks and logs to that project's **drawer in the store** (ADR-0011): `~/.loxodonta/receipts/<project-slug>/` (override the home with `LOXODONTA_HOME`), writing a `project.json` project record on the first receipt so file references stay resolvable wherever the chain lives. Resolved in Python, not by the shell, so the same settings command works on every platform (Windows included). For machine-wide recording, run `python loxodonta.py install-hook` — it writes the block above, with a SessionEnd and a SessionStart block beside it, into your user-level `~/.claude/settings.json`. Don't wire the same hook at both user and project level: both fire, and every tool call is logged twice.
- Without `CLAUDE_PROJECT_DIR`, a payload that names a `cwd` (Codex does; the Agents SDK adapter does) logs to the store drawer for that directory instead — the environment wins when both are present (ADR-0020). With neither (running the hook by hand), logs land in the working directory; `--log-dir receipts/` keeps them in one place — the hook creates the directory on first use and seeds it with a protective `.gitignore` (command history must not ride into a commit by accident). An explicit `--log-dir` outranks everything, the store included. One more variable the recorder reads: `SOURCE_DATE_EPOCH` (integer Unix seconds, UTC, the reproducible-builds convention) replaces the wall clock in every timestamp it writes, which is how `tools/demo_store.py` produces the same demo store on every run; timestamps are testimony either way, since the writer is the adversary (ADR-0002).
- **Worktrees log to the repository they belong to.** When the project directory is a git worktree, the drawer is keyed by the main repository's path, not the worktree's. Worktrees are disposable — pruned once their branch merges — so history keyed to one would be deleted by routine hygiene, losing exactly the sessions worth keeping. Every worktree's history therefore collects in one drawer. The linkage is read from the files git writes (`.git` → `commondir`), never by spawning `git`: this runs on every tool call. A worktree the harness has already deregistered still names its repository in its `.git` file, and that is enough. Anything else unreadable falls back to the project directory's own drawer rather than failing the session.
- **One session, one drawer (ADR-0023).** The drawer is decided by a session's first receipt; every later receipt of that session goes there, even if the project directory resolves differently mid-session (a worktree cleaned up under a running session was the case that found this). The hook only looks across the store when the resolved drawer holds no chain for the session yet. On the read side, a repository's recall also includes the drawers of its own harness worktrees, so a session that did get split before this rule is still shown whole.
- **One word for what leaves the machine: the profile (ADR-0031).** `install-hook --profile local|timestamped|full|custom` chooses once, at install, what leaves the machine and where; it widens no coverage and changes no entry. `local` is the flagless install: nothing leaves, an edit, a deletion or a reorder of history is caught, and a regenerated chain only against a head you keep (`head`, then `verify --expect-head`). `timestamped` is exactly `--anchor-at-session-end` under the beginner's word: a 32-byte digest of the chain head leaves at each session end, and regeneration is caught once the anchor matures. `full` is the strongest tier and the one that sends the entries themselves: `--profile full --remote URL` writes `--anchor`, `--publish "URL"` and `--publish-chain "URL"` onto the one SessionEnd command, all three to the one URL you named, because the far end tells a head from a batch of entries by content type (RECEIVER.md §4) and naming the place twice would only be a way to get it wrong. What it buys is the sentence the tier is named for: head and receipts go to a remote you name, and a wiped log survives there as of the last send. What it costs is the published-chain bullet below — every entry, action lines included — which the installer says in full before it writes anything. `--profile full` without `--remote` is a usage error (exit 64) that writes nothing and prints the two ways to have a remote: run `receiver.py serve` on a second machine the credentials here cannot reach and paste the URL it prints (docs/RECEIVER.md), or name any URL that appends what it is sent and refuses delete. `--remote` beside any other profile is refused the same way, because a remote nothing sends to reads like the entries leaving when they do not. `custom` is the raw flags, composed by hand: the four bullets below, `--anchor-at-session-end`, `--publish-head URL`, `--publish-chain URL` and `--authority URL`, each exactly what it says; the flags typed with no `--profile` are the same thing and are written down as `custom`. A raw flag beside `--profile local`, `--profile timestamped` or `--profile full` is a usage error (exit 64) naming `custom`, because the profile already says what leaves. The one exception is `--authority URL`, which composes with `--profile timestamped` and `--profile full` (ADR-0032 ruling 2): a tier can name the mechanism and never the authority, since whom to trust is the whole choice, so no tier bakes one in and the URL stays yours to type, and `--profile full --remote URL --authority URL` writes all four flags. Beside `--profile local` it is refused like any other, since nothing leaves there at all. The flagless install prints the ladder in place of a note: one line reading the choice back (the harness, the coverage, the profile), then one row per tier, each saying what leaves, the row above naming the flag that reaches it. The installer never prompts and never reads stdin. The profile is written to the coverage marker beside the matchers (below), so a change to it is as visible to the supervisor as a matcher change, and a re-run with the same profile appends nothing; beside it goes `remote`, where publishing was wired — at `full` the one URL, and under `custom` the chain's URL when one was given and the head's otherwise. `supervisor serve` reads the marker at startup and follows the strongest tier any harness declares: each harness's newest epoch speaks for that harness, and the highest tier among them (`local` below `timestamped` below `full`) speaks for the keeper, so a later flagless install for a second harness never stands a keeper down quietly, the end claim ADR-0030 ruling 2 refuses. At `timestamped` or `full` with no `--anchor-every`, the anchor keeper runs every six hours; at `full` with no `--publish-every` and no URL flag, the publish keeper runs on the same six hours to the marker's remote, the head first and the chain after it. Those six hours are the ripeness test a turn applies, not a timer: what asks the question is a clock `serve` keeps itself, which with a cadence in force takes a fresh reading of the store a minute after the last reading finished, whether or not anything is watching the page, so a `serve` left running as a background service keeps its cadences with nobody polling it (#271). A store that takes minutes to walk is read that much less often, since the minute starts when the walk ends. A turn that cannot finish at all — an unreadable store, a disk with no room — says so in one line on stderr naming the kind of failure, once rather than on every turn, because nothing else records a reading that never completed. A flag typed at `serve` wins: a URL replaces the target whole, both routes, so the marker's remote is never a second place the entries also go, and a `--publish-every AGE` typed alone at `full` changes only the cadence and keeps the marker's remote for both routes, as `--anchor-every` alone keeps the anchor. Below `full` a cadence still needs a URL beside it, and `scan` keeps that rule at every tier. `local`, or `custom` without a flag, on every harness runs no keeper, `custom` included because it wired its own session end and asked the keeper for nothing. The marker is writer-reachable, so `serve` holds its remote to the installer's rule (a plain http or https URL, nothing a shell could act on) before sending anything there; a remote that fails it is followed nowhere, and the startup line names the marker as the reason. A harness's profile is followed only while that harness's recorder is still wired: `uninstall-hook` writes nothing to the marker (ADR-0030), so the wired SessionEnd command is what says you have stopped, read from Claude Code's settings beside `--witness` and from `$CODEX_HOME/hooks.json`, and with no recorder wired the startup line says so (`publish off (profile full, claude-code; no recorder wired)`, and the same for the anchor). When the marker names an authority, the anchor keeper's turn also stamps the head it anchors, through the recorder's own `stamp`, at most once per throttle window and never twice for one head: one cadence, two commitments, and no second clock to tune (ADR-0032 ruling 3). The authority follows a rule of its own, the same shape as the tier's: the newest epoch, among each harness's newest, that names an authority at all, so a Codex install with no `--authority` never stops the keeper stamping the chains a Claude Code install asked it to stamp, and a harness re-installed without the flag withdraws only its own. It follows the wiring rule too: an authority named by a harness whose recorder is no longer wired stamps nothing, and the line says so (`not stamping (authority named by claude-code; no recorder wired)`). The marker's authority is held to the installer's rule as its remote is, and one that fails stamps nothing, the line naming the marker as the reason and never repeating the value. The line names the harness whose install named the authority, which need not be the one whose profile set the cadence, and says the stamping only when an anchor cadence is in force, since an authority with no anchor cadence sends nothing. The second startup line says each cadence, its source (flag or profile) and the harness whose profile set it. An anchor cadence that is off says one thing more: pending proofs are still upgraded on each turn, since finishing a proof already submitted is a request to a calendar too, and this line is your read-back of what leaves the machine. `serve` reads the marker and the wiring once, at start, so a re-install at another profile takes effect at the next start, and after an uninstall you restart `serve` for the keeper to stand down. On Codex, `--profile timestamped --codex` records the profile and wires no anchor at session end, because the session-end anchor stays refused there (ADR-0024); the notice says so, and the supervisor anchors on its cadence. `--profile full --codex --remote URL` records the tier and wires both publishes, with that same notice about the anchor: the two publishes go at session end and share half of Codex's three-second cap between them, the head first and the chain in what the head leaves (one window, not one budget each; the numbers are under [Codex CLI](#codex-cli)), and the digest goes on the supervisor's six-hour cadence. `--authority URL` is wired on Codex too, at either tier or under `custom`: the stamp is the last quick step in that same window and gets what the two publishes leave (the measurement is under [Codex CLI](#codex-cli)). `uninstall-hook` removes the wired command with every flag on it, at any tier, and writes nothing to the marker (ADR-0030's asymmetry).
- **Anchor at session end, if you opted in (ADR-0024).** `install-hook --anchor-at-session-end` (the mechanism the `timestamped` and `full` profiles both wire; under `custom`, the raw flag) writes `--anchor` onto the wired SessionEnd command, and from then on every session end anchors the chain head: after the tail commitment, so the head anchored is the sealed one; under a twelve-second budget inside the harness's twenty-second SessionEnd timeout; a sidecar record only for calendars that answered; nothing printed on failure, since an exit hook that complains is noise nobody can act on, and staleness is the supervisor's to surface. The budget left over goes to upgrading that drawer's pending proofs, oldest first, one request each, so a machine that never runs the supervisor still reaches Bitcoin-grade, one session late. The install command states the choice each time: a re-run without the flag turns it off and says so; `uninstall-hook` removes it with the rest. What leaves the machine is a 32-byte digest of the head, to the public calendars, from your address, only after you opted in. Codex does not get the flag: its SessionEnd hook is capped at three seconds, too short to reach a calendar with margin, so the installer refuses it with a note, and a Codex operator uses the supervisor's `--anchor-every`, or `--profile timestamped`, which records the tier and puts `supervisor serve` on its six-hour anchor cadence. What none of this survives: the agent killing the process, where the kill is the last receipt and the silence is the supervisor's alarm.
- **Publish the head at session end, if you opted in (ADR-0025).** `install-hook --profile full --remote URL` wires this route in one word, and `--publish-head URL` under `custom` is the raw flag; either writes `--publish "URL"` onto the wired SessionEnd command, and from then on every session end POSTs the chain head to that URL: after the tail commitment, so the head that leaves is the sealed one, and before the chain, the stamp and the anchor, so nothing slower can ever cost the one POST; the anchor takes what is left of the twelve-second budget. What leaves is one JSON body with `head`, `n`, `session`, `ts`, `event`, and one readable line under both `text` and `content` (Slack and Teams render one key, Discord the other); nothing else, no path, no project name, no action line, no chain bytes. The POST waits at most three seconds, name lookup included, and is then left behind; a redirect is a failure, so the head goes to the URL you wrote or nowhere; nothing is printed and the hook never fails over it. The URL must be plain http or https with nothing a shell could act on, because the wired command runs through a shell: the installer refuses anything else. Which remotes count as a head record, and why a gist under your login does not, is ADR-0025 and GLOSSARY *Head record*; the check a published head enables is `verify --expect-head` with a head copied from the channel. Like the anchor flag, the install command states the choice each time, a re-run without the flag turns it off and says so, and `uninstall-hook` removes it with the rest. Codex gets the flag too, with a tighter bound: its whole SessionEnd hook is capped at three seconds, so every quick step of a Codex session end shares one window of 1.5 seconds, and the head, which goes first, waits at most all of it rather than three (the measurement is below, under [Codex CLI](#codex-cli)). A session that never reaches its end (the bad day: the hook was stripped, so no session end fired) is the supervisor's keeper's to cover: `supervisor scan|serve --publish-every AGE --publish-url URL` publishes an aged head once, through `loxodonta publish`, and the scan report says per chain when a head last left the machine (docs/TOUR-SUPERVISOR.md §2).
- **Publish the chain at session end, if you opted in (ADR-0031 rulings 2 and 3).** `install-hook --profile full --remote URL` wires this route in one word, beside the head and the anchor, and `--profile custom --publish-chain URL` is the raw flag on its own; either writes `--publish-chain "URL"` onto the wired SessionEnd command, and from then on every session end POSTs that chain's entries to that URL: after the head publish and before the stamp and the anchor, so the five steps run in the order the bullets set — commitment, publish head, publish chain, stamp, anchor — and the anchor still takes what is left of the twelve-second budget. This is a different trade from the head's, and the installer says so before it writes anything: **every entry leaves this machine** — the timestamp, the actor, the action line and the file references — and action lines are command lines, so anything the agent typed can ride out with them, a pasted secret included. Not only the sessions still to come: the keeper walks every chain in the store and sends each from its first entry, so once `supervisor serve` publishes (at `full` with no flag typed, under `custom` when it is given `--publish-chain`), last month's sessions leave too, and the installer says that in the same breath. What the head publish sends is a digest, a count and one readable line; what this sends is the flight recording. Pick a remote that can only add, never delete, and that you would trust with command lines: `receiver.py` is the one this repo ships (docs/RECEIVER.md), and the file it writes verifies `VALID` with `loxodonta verify --log` once the session has ended. What leaves is the chain's lines exactly as they sit on disk, newline-delimited, under `Content-Type: application/x-ndjson`, with the chain's file name, the session, the `n` range and the head in headers named for the tool — the wire contract is RECEIVER.md §4, and nothing else goes. The first send to a remote starts at genesis; every later one starts after the last entry that remote acknowledged, which the publish memo remembers as a row of kind `chain` carrying `first`, `last`, the head after that entry, the time, the event, and `remote_id`: a fingerprint of the remote, the first 16 hex characters of the SHA-256 of the URL, and never the URL, which carries the credential. That row is written only on a 2xx, so the cursor never passes an entry that did not land. The cursor is per remote (#263), so a new remote receives each chain from its genesis and its file verifies like the first one's: however the chain comes to point at a remote that has taken nothing (a re-run of `install-hook --profile full --remote NEW`, a changed `--publish-chain`, a keeper pointed elsewhere, two harnesses naming two remotes), the send there starts at entry 0, and a remote sent to before resumes where it stopped. A row written by a recorder from before the fingerprint names no remote and counts for none, so after the upgrade each chain goes once more from genesis, to wherever it goes next, and a receiver that already holds it keeps its file unchanged, having dropped every line as an exact duplicate. A head is not kept per remote: its row names none, and a head is posted once, wherever it went. One batch stays under the receiver's 8 MiB cap; a longer tail goes in several, each acknowledged on its own. A refused, timed-out or cut-off send appends the attempt row below (step `publish-chain`) and no chain row, so the same lines go again next time and the remote drops the duplicates. Like the other flags, the install command states the choice each time, a re-run without it turns the chain off and says so, and `uninstall-hook` removes it with the rest. Codex gets the flag inside the same window as the head: its whole SessionEnd hook is capped at three seconds, so the send gets what the head left of the shared 1.5 seconds, each batch waiting no longer than what remains of it, sends the batches that fit and leaves the rest at the cursor — a short clock costs batches, never entries. The keeper is the cover for the rest, and for the session that never reached its end: `supervisor scan|serve --publish-every AGE --publish-chain URL` sends the entries after the cursor on its cadence, after the head when both are wired, at most once each per turn — and at `full` `serve` needs no flag at all, since it reads the marker's remote and runs both routes on the six-hour default.
- **Stamp the head with an authority at session end, if you opted in (ADR-0032).** `install-hook --authority URL`, at `--profile timestamped` or `--profile full` or under `custom`, writes `--stamp "URL"` onto the wired SessionEnd command, and from then on every session end asks that RFC 3161 timestamp authority for a token over the chain head: after the tail commitment, so the head stamped is the sealed one, and after the published head and the published chain and before the anchor, so the slow calendar can never cost any of the quick steps; the anchor takes what is left of the twelve-second budget. What leaves is a DER `TimeStampReq` — version 1, a SHA-256 imprint of the head, a nonce, `certReq` true — posted as `application/timestamp-query`; the same 32-byte digest the anchor sends, and nothing else. The recorder reads only whether the authority granted it and keeps the whole response verbatim, base64, in its own sidecar `<log>.stamps.jsonl` beside the head, that head's `n`, the time asked and the authority's URL, which is written down because it is not a credential (docs/ANCHORING.md §6). It never parses the token. The query waits at most three seconds, name lookup included, and is then left behind; on a Codex hook, only what the head and the chain left of the shared 1.5-second window, and Codex has the flag because that one POST was measured inside its three-second cap the way #183 measured the head ([Codex CLI](#codex-cli) below). Nothing is printed and the hook never fails over it. The URL must be plain http or https with nothing a shell could act on, like the publish URL, because the wired command runs through a shell. The flag is the one raw flag a tier takes, because a tier would otherwise have to choose an authority for you. The supervisor's keeper covers the session that never reached its end, on the anchor cadence and never a cadence of its own: when the marker names an authority, each ripe head that has no token gets one on the turn that anchors it. What it adds over the anchor is speed and standing, and what it costs is the difference in kind: a token is somebody's signed word where an anchor's proof is nobody's product, so the two never share a word. Judging it is `verify --stamps --authority-chain FILE` through `openssl`, or the honest note that nobody judged it; save the authority's certificate chain the day you wire the flag.
- **Each session-end step writes down how it went (#240).** The anchor, the two publishes and the stamp are quiet on failure by design, and quiet at the moment is not the same as silent in the record: after each step the hook appends one row of kind `attempt` to the sidecar that step already owns, the anchors sidecar (`<log>.anchors.jsonl`) for the anchor, the publish memo (`<log>.published.jsonl`) for either publish, and the stamps sidecar (`<log>.stamps.jsonl`) for the authority timestamp. The row carries the step (`anchor`, `publish-head`, `publish-chain`, `stamp`), the time, the budget in seconds the step had, and the outcome: `submitted`, `sent` or `granted`, or the one line the step produced, such as `no answer within 3 seconds`, `the remote answered 404`, or `no calendar answered within 12 seconds`. A quick step (the two publishes and the stamp) that found the session-end window already spent by the steps before it does not start, and its row says `the session-end window closed before this step` with a budget of 0, so a step that never ran is told apart from one that was never wired. Never the URL, which is a credential: the outcome line is what the socket said or the exception's bare name, so a TLS certificate-name mismatch surfaces the public hostname inside the reason text, the host and never the secret. A head already anchored at session end leaves no row, since the anchor step did not run; a chain with nothing after the cursor leaves none either, and a head that already holds a token, for the same reason. The session end writes most of these rows; `publish`, `publish --chain` and `stamp` also write one when a query of theirs fails, since those verbs are what the supervisor's keeper runs on its cadence: without that row, a failure on the keeper's turn was readable for one tick of one scan and then gone. The row is testimony and never a proof: `verify --anchors`, the supervisor's keeper and `verify-package` skip it by its kind, so a sidecar holding only attempt rows reads as an empty one. What reads it is the supervisor: `scan --json` carries per chain `left` (when something last left the machine and by which door: `published` for a head, `published-chain` for a batch of the entries, `anchored` for a digest) and `last_failed` (the last step that failed: step, time, outcome), cadence or no cadence; the dashboard's project tile shows both; and when the wired SessionEnd command carries a publish flag and no chain here holds what that route sends — a sent head for `--publish`, an acknowledged batch for `--publish-chain`, each route read on its own, and a batch counting only for the remote `--publish-chain` names (#263) — the report says so in one sentence under `published`, naming the route that has been silent. The chain's schema is untouched: a note about network luck is not part of the session's history.
- **Read one body before you wire a real remote.** `tools/publish_echo.py` listens on the loopback address, prints every POST it takes with the field names beside it, and answers 200, so the sentence above about what leaves is something you check rather than take on trust: run `python tools/publish_echo.py`, then either point one session end at `http://127.0.0.1:8787/head` or send a head by hand with `loxodonta publish --log LOG http://127.0.0.1:8787/head`. `--port 0` takes a free port and prints it; `--once` stops after the first body. An address on this machine is not a head record and never a place to publish to — it fails both halves of the test in GLOSSARY *Head record*, since the head has not left and nothing there is beyond the writer's reach. It is a window onto the body, and the wired URL should be a remote the credentials here cannot delete from.
- **Parallel tool calls share one chain, so the hook serializes itself.** A harness fires one hook process per tool call and runs tool calls concurrently; each append therefore takes an exclusive `<log>.lock` across read-tail-then-append (ADR-0004). Without it, racing writers tear a line or — more often — silently drop a receipt from a chain that still verifies `VALID`. Waiting writers retry for `RECEIPTS_LOCK_TIMEOUT` seconds (default 10) and then **fail loudly**: a missing receipt is the one thing this tool exists to prevent, so contention is never a quiet skip. A lock left untouched for 60s is treated as abandoned and broken, so a crashed writer cannot wedge a chain forever.
- **A damaged chain is retired, not repaired.** If the chain the hook would extend has a torn tail, it starts a sibling — `receipts-<session>-002.jsonl` — and records there. The damaged chain is left byte-for-byte as evidence (there is no repair command, by design: ADR-0002). Each sibling is a complete chain with its own genesis and head, and **anchors separately** — worth knowing before you rely on one head record per session. The `log` and `run` commands still refuse to extend a damaged tail; siblings are the hook's answer, because a harness cannot stop and ask.
- The shipped `matcher` is `"*"` — every completed tool call, reads and fetches included (ADR-0016): the forensic record must cover where an attack *enters* (reads of untrusted content) and *leaves* (network and MCP tools), not just where it changes state, and MCP tool names can't be enumerated in advance. You can narrow it (e.g. `"Edit|Write|NotebookEdit|Bash|PowerShell"`, the old default) to receipt only state-changing tools — but every uncovered tool call is a blind spot, and if you narrow, include every shell tool your harness actually runs: the desktop app on Windows issues most commands through a `PowerShell` tool, and a matcher that omits it silently misses those sessions' work. `install-hook` widens the old shipped default in place when it finds it, leaves any other matcher alone, and prints a notice; the supervisor observes matcher changes and judges each session by the coverage in force at its time, so changing your matcher never manufactures deficits over old sessions.
- The adapter reads `session_id`, `tool_name`, and `tool_input` from the payload, plus `cwd` (only when `CLAUDE_PROJECT_DIR` is unset) and `transcript_path` (for the commitments below); nothing else. `tool_response` is never read: tool output is deliberately not recorded (`.out-of-scope/001`) — receipts are not transcripts, and `action`/`path` values are plaintext forever (SPEC §8: no secrets).

## What gets written

- **One chain per session**: `receipts-<session_id>.jsonl`, auto-initialized on first use — plus a `-002` sibling if that chain is ever damaged (above). Separate sessions get separate chains; interleaving them is `report`'s display concern, not an integrity concern. Note the two senses of *sibling*: parallel **sessions** each get their own chain because they are separate histories, while a damaged chain gets a sibling because history must continue somewhere. Within one session, parallel tool calls share a chain and are serialized (SPEC §8, ADR-0004).
- **actor** — `claude-code` by default; the installers name the harness (`codex`), the SDK adapter names itself (`openai-agents`), and `--actor` overrides. On a machine running several harnesses, recall rows say which one acted.
- **action** — the tool name plus its most descriptive argument, collapsed to one line: `Bash: pytest -q`, `Write: src/main.py`. The argument is chosen by key, in preference order (`file_path`, `notebook_path`, `command`, `path`, `pattern`, `url`, `query`, `prompt`), with `summary` last as the adapters' fallback for tools whose arguments carry none of the named keys; a tool with no usable argument records its name alone.
- **files** — a `{path, sha256}` fingerprint for `file_path` / `notebook_path` arguments that sit under the **project** and still exist after the call, recorded relative to the project root (SPEC §3 as amended v0.1.1, ADR-0012). Files outside the project (or already gone) are skipped, never fatal: a hook that fails the session over path layout teaches the operator to turn the hook off — the receipt still records the action itself. *Under the project* is judged on the path as given, never on where it leads (SPEC §3): a symlink inside the project is followed, and the receipt carries the link's path with the hash of the target's bytes at that moment, even when the target sits outside. Only a regular file is fingerprinted, so a directory, a FIFO or a device at that path is skipped the same way. `log --file`, `run --file` and `verify --files` have no such guard and read whatever the path opens: at a FIFO they wait until a writer opens it and read until that writer closes it, and at a link to a device like `/dev/zero` they never finish, so `verify --files` gives no verdict. With the `"*"` matcher this includes **read** tools: a `Read` receipt fingerprints the file as it was when the agent saw it — for a forensic rebuild, "what content did the agent ingest" is exactly the question — and `verify --files` judges by a file's *latest* reference, so a read fingerprint never manufactures divergence noise. One caveat: the hash covers the whole file on disk, not the slice a ranged read returned; it identifies the artifact, not the excerpt.

## Coverage and cost

Wide coverage is one fresh hook process per tool call, machine-wide. Measured on the author's machine (Windows 11, CPython 3.13, NVMe): **~135 ms median per call, p95 ~158 ms**, end-to-end — cold interpreter spawn, payload on stdin, locked append. Chain length doesn't move it: appends to a ~380-entry chain measure the same 134 ms median, so a session never slows down as its history grows. Interpreter startup dominates everything.

Where the real limits sit:

- **Across sessions there is no contention.** Chains are per-session and locks per-chain, so any number of simultaneous agents record independently — the store's limit is your disk, not a shared lock.
- **Within one session**, parallel tool calls serialize on the chain's lock (ADR-0004, above). At ~135 ms per append, a burst of dozens of concurrent calls in a single session can stack toward the 10-second lock timeout — and the hook then **fails loudly** rather than skipping. If your harness fans out very wide inside one session, that is the edge to watch; nothing in the field has reached it.
- **The store is a log store — treat it like one.** Action lines are one-line, 160-character summaries, never transcripts, and never tool output (SPEC §2, §8) — but with `"*"` they include URLs fetched, queries searched, and prompt heads, because in a forensic reconstruction those *are* the evidence (a receipt that scrubbed the exfiltration URL would faithfully prove nothing). The chain deliberately holds evidence, so give `~/.loxodonta/` the handling you give logs: local ACLs, keep it out of backups that leave the machine, and never commit it (the drawer's `.gitignore` guards the accident, not the policy). Remember the recall digest is injected into session context — everything in a chain is discoverable by whatever reads that context, which is one more reason receipts must never contain secrets.

`install-hook` also writes down what it wired, in `~/.loxodonta/coverage.json`: one appended entry per change, carrying `since`, `matchers`, the `harness` whose settings file it touched (ADR-0030), the `profile` chosen (ADR-0031), the `remote` publishing was wired to when it was — the one URL at `full`, and under `custom` the chain's when one was given and the head's otherwise — and, when one is named, the `authority` the head is stamped by (ADR-0032); the marker never travels, so unlike the publish memo it may hold a URL. `serve` follows the `remote` only at `full`, the tier that asked the keeper for a cadence. The supervisor reads that file to date coverage from when it began rather than from its own first look, which matters because the documented install order puts a week of work between the two. It is testimony and writer-reachable, like every setting on the machine: it records what the operator asked for, and the supervisor calibrates from it (merged in memory, never copied into its baseline) and steers its keeper by it. A writer that edits it can redirect the keeper or silence it, just as it can edit the wired command itself (ADR-0025 names that); what shows the gap is the remote's own record, where heads and entries stop arriving, or never arrive where the operator is looking. `uninstall-hook` writes nothing: a start claim says more calls owe receipts, an end claim says fewer, and "nothing was owed from here" is the one sentence that could retire the completeness alarm.

Failure semantics: on an unusable payload or an unappendable log the adapter prints one error line and exits 1 — visible in the harness, non-blocking for the session (the tool already ran; PostToolUse cannot roll it back, and receipts wouldn't want to).

## The transcript commitment (ADR-0017)

The chain is the *spine* of a forensic rebuild; the flesh — full commands, tool output, the conversation — lives in the harness transcript, a plain file the writer can reach. Every 25 entries, the hook staples the two together: it hashes the transcript **from byte zero** and appends a bookkeeping entry in the recorder's own voice —

```
{"actor": "receipts", "action": "transcript-commitment: bytes=1679210 sha256=c01237…", "files": [], …}
```

A committed prefix can never be rewritten undetected again: `verify --transcript` re-hashes each committed boundary and says which commitments hold (SPEC §2.2, §6). Because each commitment covers the whole prefix, a diverging one localizes the rewrite to the span since the previous commitment. `supervisor scan` hands each committed session its exact judge command.

The honest limits, stated plainly:

- **The window before the next commitment is open.** Bytes newer than the latest commitment — including the whole transcript during the first 25 calls — are rewritable until a commitment covers them, and the commitment will faithfully fingerprint whatever is there by then. At most ~25 calls of history are exposed at any moment.
- **The tail commitment depends on the client.** A SessionEnd hook writes one final commitment over the whole transcript, whatever the cadence position (issue #79) — but only where the client actually fires SessionEnd. The terminal CLI does, reliably, on `/exit` and Ctrl-D. Claude Desktop's Code mode offers no `/exit` and its SessionEnd behavior is undocumented, so sessions there commonly end with an **uncommitted tail** — the final <25 calls' bytes never locked in. The supervisor says so honestly ("tail uncommitted", ADR-0018) and its **tail keeper** closes the gap from the reading side: the scan writes the missing exit commitment itself, shrinking the open window to one scan cadence. A hard kill anywhere fires nothing, and the docs keep saying so.
- The commitment is **writer-authored**, like everything the recorder writes: it extends tamper-evidence to the transcript *by reference, forward from each commitment* — detection latency, not protection. Anchors remain the only hard boundary.

Cost: a commitment is one extra append (~4% more entries) and one transcript read+hash at the boundary — measured at ~1 ms per MB, inside a ~155 ms hook call that interpreter startup dominates either way (EXPERIMENTS §4). Bookkeeping entries never count against the completeness witness and never spend digest rows.

## Other harnesses

The hook payload is the adapter contract (ADR-0020): whatever the harness, an integration produces this payload and hands it to `loxodonta hook`. Nothing else writes the chain. Two adapters ship.

### Codex CLI

Codex's hooks (GA since 2026-05) send a `PostToolUse` payload with the same fields Claude Code sends — `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, `tool_response` — plus `turn_id`, `model`, `permission_mode`, `tool_use_id`, which the recorder ignores. The one difference that matters: Codex sets no `CLAUDE_PROJECT_DIR`, so the recorder takes the project from the payload's `cwd` (above). Wire it machine-wide:

```
python loxodonta.py install-hook --codex
```

That writes three blocks into `$CODEX_HOME/hooks.json` (default `~/.codex/hooks.json`), idempotently, keeping any hooks already there and backing the file up first: a `PostToolUse` block on matcher `.*` (Codex matchers are regexes; this is its every-tool-call) running `loxodonta.py hook --actor codex`, a `SessionEnd` block for the tail commitment with a 3-second timeout, which is Codex's cap for that event, and a `SessionStart` block running `supervisor.py digest --payload` so a Codex session opens with the same recall digest a Claude Code session does. The `--payload` flag is the one Codex-specific wrinkle: Codex sets no `CLAUDE_PROJECT_DIR`, so the digest reads the SessionStart payload on stdin and takes the repo from its `cwd` (the environment still wins when a harness sets it). The digest never reads stdin unasked, because under `supervisor mcp` stdin is the wire. **Codex asks you to review new hooks once** — open Codex and run `/hooks` to trust them; until you do, nothing records, and the installer says so. `uninstall-hook --codex` removes exactly those three entries.

Honest differences from the Claude Code wiring:

- **Coverage reads slightly differently.** Codex fires `PostToolUse` after a shell command with a non-zero exit, where Claude Code fires nothing for a failed call. Both are recorded outcome-blind, so a Codex chain has receipts for attempts that failed and a Claude Code chain does not. Neither is wrong; they are what each harness owes.
- **The head publishes at session end, on a shorter clock (#183).** ADR-0025 ruling 3 held `--publish-head` back for Codex until one POST inside the three-second cap had been measured. Measured on the author's machine (Windows 11, Python 3.13, a 157-entry chain and a 2 MB rollout transcript to seal), timing the whole wired command through a shell the way Codex runs it, seven runs of each:

  | what the SessionEnd hook did | median | worst |
  |---|---|---|
  | sealed only, no publish | 0.20s | 0.21s |
  | published, receiver answered 200 | 0.26s | 0.32s |
  | published, name did not resolve | 0.26s | 0.28s |
  | published, connection refused | 2.28s | 2.30s |
  | published, remote silently dropped it | 3.21s | 3.22s |

  The POST costs 0.06s over the seal, and a real remote adds little: the DNS, TCP, and TLS handshake to `hooks.slack.com`, `discord.com`, and `outlook.office.com` measured between 0.01s and 0.07s from here, no request sent. So the success path fits the cap many times over, and the failure paths are what the full three-second wait could not survive: a remote that silently drops the request costs the whole wait and lands past the cap. Most of the refused-connection row is the operating system rather than the wait: Windows takes two seconds to report a refused connection, measured on the bare connect, whatever timeout is asked of it.

  Codex therefore gets the flag with the POST cut off at half the cap, 1.5 seconds. Re-measured after the change, the Codex hook's worst case landed between 1.7s and 1.9s against a cap of three, where the same sitting remote still held the default wait to 3.2s. What a cut-off POST misses, the supervisor's keeper publishes later (`--publish-every`).

  Those 1.5 seconds are one window for the whole session end, not one per step (#262). The chain and the stamp joined the head after #183, each with a 1.5-second budget of its own, and nothing bounded their sum: the `full` tier wires the head and the chain to one remote, so the ordinary bad day, that remote down, put a Codex hook past the cap, where Codex stops it from outside and the step it stopped never writes its attempt row. Now the head, the chain and the stamp share the window in that order, each POST waiting its own 1.5 seconds or what the steps before it left, whichever is less, each batch of the chain included; a step with nothing left does not start and writes `the session-end window closed before this step`. Measured the same way (Windows 11, Python 3.13, a chain of some 170 entries, a 2 MB transcript, `--actor codex` through a shell, seven runs each, both columns in one sitting), with each silent remote taking the connection and never answering:

  | what the SessionEnd hook did | one budget per step (median, worst) | one window (median, worst) |
  |---|---|---|
  | sealed only, no publish | 0.22s, 0.26s | 0.21s, 0.23s |
  | `full`: head and chain to one silent remote | 3.27s, 3.30s | 1.73s, 1.78s |
  | head, chain and stamp, all silent | 4.75s, 4.76s | 1.73s, 1.75s |
  | head answered, chain and stamp silent | 3.29s, 3.34s | 1.69s, 1.72s |
  | stamp alone, authority silent (#251's run, a 0.15s floor) | 1.67s, 1.68s | 1.66s, 1.67s |

  However many remotes sit silent, the hook now ends where one silent POST ended it under #183, and every wired step leaves its row: in the three-silent run, the head's says `no answer within 1.5 seconds` and the chain's and the stamp's say the window closed; in the last run the head's says `sent` and the chain waited the 1.4 seconds the head left. So a Codex session end sends what fits and the keeper resumes the rest from the cursor. Claude Code's hook keeps its budgets: its twenty-second timeout already holds three silent steps at three seconds each and the anchor inside the twelve-second window the anchor already shared with them, so the window changes nothing there but that a batch of the chain can no longer outrun its step.

  What that margin rests on: the seal hashes the whole transcript before the POST begins, so a long session's rollout file is part of the floor, and nothing bounds the seal the way the cutoff bounds the POST.

  | transcript sealed | floor | with the 1.5s cutoff | margin under the cap |
  |---|---|---|---|
  | 2 MB | 0.23s | 1.73s | 1.27s |
  | 53 MB | 0.30s | 1.80s | 1.20s |
  | 210 MB | 0.83s | 2.33s | 0.67s |
  | 524 MB | 1.04s | 2.54s | 0.46s |

  Half a gigabyte of transcript still fits, with the margin down to half a second. A transcript far past that is the case these numbers do not cover.

- **The head is stamped at session end too, last in the same window (#251).** ADR-0032 held `--authority` back for Codex until the stamp's one POST had been measured inside the cap the way the head's was. Measured on the same machine (a 164-entry chain and a 2 MB rollout transcript to seal, the wired command run with `--actor codex`, seven runs of each), the query costs 0.07s over the seal when the authority grants a token, the head publish's 0.06s within noise: one POST of about 100 bytes, and a reply of a few kilobytes of token read in one go. The silent cases are the window's, in the table above: the stamp alone against a silent authority ends the hook at 1.67s worst, and after a head that answered, the stamp waits the 1.4 seconds the head left and the hook ends at 1.62s worst. So Codex has `--authority`, the stamp the last quick step in the window and taking what the two publishes leave; what a cut-off query misses, the supervisor's keeper asks for on the anchor cadence.

  The session-end anchor stays refused for Codex, and the refusal is the installer's: `install-hook --codex --anchor-at-session-end` exits with a note, because 1.5 seconds is a POST and not a calendar round trip. The hook enforces nothing itself, so a hand-edited `hooks.json` carrying `--anchor` on a Codex SessionEnd command would still try the calendars and Codex would kill it. A Codex operator anchors with the supervisor's `--anchor-every`, or chooses `--profile timestamped`: the installer records the tier, wires no anchor, says so, and `supervisor serve` anchors every six hours on the profile's word.
- **No completeness witness yet.** The supervisor's completeness alarm (exit 6) counts owed receipts by reading Claude Code's transcript layout. Codex's rollout transcript (`$CODEX_HOME/sessions/…/rollout-*.jsonl`) is a different layout that Codex documents as unstable, so Codex sessions get integrity, recall, anchoring, and the baseline tripwire — everything except the alarm that says "this session is live and its receipts stopped". Transcript commitments do work: they hash bytes, not shapes, so the rollout file is committed every 25 entries and sealed at SessionEnd exactly as a Claude Code transcript is.
- **The digest arrives as developer context.** Codex adds a SessionStart hook's plain-text stdout to the model's context, so the digest lands the same way it does in Claude Code. The same memory is also reachable over MCP for anything Codex runs that wants to ask for more — [docs/MCP.md](MCP.md).

### OpenAI Agents SDK

`adapters/openai_agents.py` is a `TracingProcessor` that turns the SDK's spans into hook payloads. Three lines in your program:

```python
from agents import add_trace_processor
from adapters.openai_agents import ReceiptRecorder
add_trace_processor(ReceiptRecorder())
```

Each run's trace becomes one chain — `receipts-<trace_id>.jsonl` in the drawer for the program's working directory (pass `project=` to name another) — and `supervisor digest`, `search`, and the MCP server read it exactly as they read a Claude Code session. Recorded: `function` spans (every function tool, and MCP tools, which the SDK wraps as function tools) and `handoff` spans (`handoff: coder -> reviewer`). Not recorded: model turns, guardrails, and hosted server-side tools, which are not actions on this machine. A tool that raised still leaves its receipt — the span fires either way, which is why the adapter listens to spans rather than the SDK's `on_tool_end` hook, which does not fire for a raised tool. Tool arguments are summarized by the same key rules as above; with `trace_include_sensitive_data=False` the arguments are absent and the line carries the tool name alone.

The adapter is stdlib only and imports the SDK only if present, so it reads and tests as plain Python. It is synchronous on purpose: one recorder process per tool call (~135 ms, below), in span order, nothing lost if the program dies. A recorder failure is printed to stderr and never raised — the run must not die over its flight recorder, but a silent recorder is worse than a loud one. Register it with `set_trace_processors([ReceiptRecorder()])` instead of `add_trace_processor` if you also want to stop the SDK's default export to OpenAI; do not use `set_tracing_disabled(True)`, which silences every processor including this one.

**The trust position is one ring closer to the writer than a harness hook, and this page will keep saying so.** A Codex or Claude Code hook is a process the harness spawns after the call: outside the agent program entirely. The SDK processor runs inside the agent program's own process. The model still cannot skip a receipt — the SDK fires the processor, not anything the model controls — but the program's author can (by not installing it), and a tool the model runs could edit the program's source. Completeness is the integration's job (GLOSSARY: *Completeness*); this is the integration, and this is its boundary. As with Codex, there is no completeness witness for SDK runs.

### Writing another adapter

Produce the payload, call the hook. The minimum is `session_id` (one chain per value), `hook_event_name: "PostToolUse"`, `tool_name`, `tool_input` (a dict; use a named key or `summary`), and `cwd` (the project). Add `transcript_path` if the harness keeps one and you want commitments. Send `hook_event_name: "SessionEnd"` with the same `session_id` and `transcript_path` to seal the tail. Pipe it as UTF-8 JSON to `python loxodonta.py hook --actor <harness>`; exit 0 means the receipt is on the chain, anything else comes with one line on stderr. That is the whole contract, and the hook's own test suite is your test suite.

## Verifying a session

```
loxodonta verify --log receipts-<session>.jsonl            # chain integrity
loxodonta verify --log ... --transcript <transcript.jsonl> # + judge transcript commitments
loxodonta report --log receipts-<session>.jsonl            # human timeline
loxodonta anchor --log receipts-<session>.jsonl            # pin it to Bitcoin (Stage B)
loxodonta verify --log ... --expect-head <head from your channel>  # against a published head (ADR-0025)
```

The operator ritual from ANCHORING.md §5 applies unchanged; session chains are ordinary receipt logs.
